### P1. `relaunch` 后测试钩子环境变量丢失，任务第 4 项的原始验证步骤无法读 state

- **现象**：`crosscheck 1` + `relaunch` 后，新测试副本进程确实启动（pid 30640），但 `ui.py state` 返回 `TIMEOUT`。原因是 `AppLanguage.relaunch()` 用 `NSWorkspace` 新开自身实例，`GPXPV_UITEST_DIR` 不会继承到新进程；`UITestHook` 只在启动时读一次该环境变量。
- **复现步骤**：
  ```sh
  pkill -f Tests/ui/app.noindex/GPXPointViewer.app
  open -n --env GPXPV_UITEST_DIR=$HOME/Library/Containers/de.wayne.GPXPointViewer/Data/tmp/uitest \
    Tests/ui/app.noindex/GPXPointViewer.app --args -AppleLanguages '(zh-Hans)'
  python3 Tests/ui/ui.py "crosscheck 1" "relaunch"
  sleep 10
  python3 Tests/ui/ui.py state
  ```
- **期望 vs 实际**：期望 `state` 返回含 `"crossCheck":true` 的 JSON；实际 `TIMEOUT`，且 `pgrep` 能看到新实例。持久化本身正确：容器 plist `fillCrossCheck=True`；手动带 `GPXPV_UITEST_DIR` 重启后 `crossCheck=true`；`crosscheck 0` 后 plist 为 `False`、重启后 `crossCheck=false`。
- **影响**：仅测试钩子/测试文档；普通用户从 Finder 重启 app 不受影响（不需要该环境变量）。**不阻塞发布**，但第 4 项的文档写法需要修正，否则以后无法按原步骤回归。
- **相关日志**：容器偏好 `~/Library/Containers/de.wayne.GPXPointViewer/Data/Library/Preferences/de.wayne.GPXPointViewer.plist`；无截图（锁屏且本轮不依赖截图）。

### P2. UI 回归首轮 B13 出现一次钩子 IPC 读错误，重跑不复现

- **现象**：首轮 `run_crosscheck_tests.py` 的 B13 第一次 `batchnextconflict` 返回：
  ```text
  read error: Error Domain=NSCocoaErrorDomain Code=260 "未能打开文件“cmd”，因为它不存在。"
  UserInfo={NSFilePath=.../uitest/cmd, NSURL=file:///.../uitest/cmd,
  NSUnderlyingError=... {Error Domain=NSPOSIXErrorDomain Code=2 "No such file or directory"}}
  → batchnextconflict selected=1792193914.0
  ```
  断言要求两次结果都含 `selected=` 且不同；第一次是错误文本，故 B13 FAIL，`FAILS: ['B13 ...']`，exit 1。
- **复现步骤**：
  ```sh
  pkill -f Tests/ui/app.noindex/GPXPointViewer.app
  python3 -u Tests/ui/run_crosscheck_tests.py 2>&1 | tee /tmp/xc_ui.log
  ```
  同一命令重跑一次：B13 正常 `batchnextconflict selected=1792193914.0 → 1792194141.0`，全部 `FAILS: none`，exit 0。复现率约 1/2 次（第二次未复现）。
- **期望 vs 实际**：期望每次命令都返回 `batchnextconflict selected=<id>`；实际偶发 app 端在 `UITestHook.poll()` 的 `String(contentsOf:)` 读取 `cmd` 时抛 ENOENT，随后 `fileExists` 为 true，写入 read error 并删除 `cmd`。从代码看是测试钩子轮询与 `ui.py` 原子替换 `cmd` 之间的竞态（`GPXPointViewer/UITestHook.swift:99-108`），不是精确模式业务逻辑失败。
- **影响**：仅测试稳定性；重跑全部功能断言通过。建议测试驱动对这类 `read error` 重试，或让钩子读取失败时不写 `out.txt`、不删除新 `cmd`。**不阻塞发布**。
- **相关日志**：第 2 次完整日志 `/tmp/xc_ui.log`（52 行，`FAILS: none`）；第 1 次错误见上（会话终端输出，未落盘）；无截图。

### P3. `batchplan` 自动「地图判段」会真实请求 Overpass，严格「全部离线」未做到

- **现象**：按任务第 3/5/6/7 项执行 `batchplan` 时，app 自动调用 `resolveTripsByMap()`（`GPXPointViewer/TrackStore.swift:2746`），进而调用 `RoadNetwork.nearestRailDistances()`（`GPXPointViewer/RoadNetwork.swift:881-895`），向公共 Overpass 端点 POST 查询 150 m 内铁路。`fakeroute` 只覆盖 OSRM/Valhalla 路线请求，**不覆盖 Overpass**。状态证据：`offline=false`、`network=null`；`trips` 中出现 `mapRail`/`mapRoad`/`mapVerdict`，例如第 2 段 `{mapRail:0,mapRoad:8,mapN:0,mapVerdict:"road"}`；首次 `batchplan` 后 `tripMapRunning` 持续 >90 s（符合 Overpass 公共实例 30–60 s 排队特征），后续 `batchplan` 因内存缓存立即为 false。
- **复现步骤**：
