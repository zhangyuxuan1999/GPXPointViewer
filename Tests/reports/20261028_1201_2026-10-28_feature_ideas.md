### 5. 产出建议书

#### 1. 我理解的这个 app

- 单用户 macOS 原生足迹整理工具：GPX / 一生足迹 CSV / `.fwdb` 存档导入，Apple 地图 + 自写 Metal 点云，百万级点仍可交互。
- 核心价值不是“看轨迹”，而是把多年备份**洗干净**：断档补点（OSRM/Valhalla 公路、Overpass 铁路）、回放点/乱跳清理、修改记录可还原。
- 世界迷雾口径的迷雾/地区统计/时光机/视频/图片导出，把数据变成可看的成果。
- 数据来自 Garmin 记录仪 + 手机，典型场景是欧洲自驾/火车长途，痛点是隧道、失锁、脏点。
- 设计哲学：**本地优先、公共服务按需少请求、结果可审阅可回滚、性能走 Accelerate/Metal/并行**。

#### 2. 功能建议（24 条）

> 除特别注明外均**离线**，不增加 OSRM/Valhalla/Overpass/瓦片请求。涉及 OSM 派生几何的导出保留 `© OpenStreetMap contributors` / ODbL 署名；涉及 Apple 底图的导出只做本地个人使用，不默认分发。

**数据质量与补点**

1. **双设备互证补点**（用另一台设备同一时段的轨迹填本设备的断档）
   - 为什么：用户同时有 Garmin 和手机；一台进隧道失锁时另一台可能还在记。现有补点只能靠路网猜，铁路/隧道群尤其需要真实旁证。
   - 怎么做：把 `Tests/probes/tunnelprobe*.swift` 的时间窗对齐思路产品化；`TrackStore` 增加 witness track，`GapDetector` 候选在 `(tA,tB)` 内取旁证点，时间偏移用重叠段中位数估计；生成 `RouteDraft(source: .witness)`，`ChangeLog` 记来源；仍走 `FillPlausibility` + 审阅，不自动落地。离线。
   - 工作量与风险：**M**；旁证也可能漂移/缺时间，偏移估计错误会填错，默认只建议不自动落地。

2. **断档候选手动合并/拆分**（修正自动隧道群合并的边界）
   - 为什么：自动规则是“相邻断档间 ≤3 点、≤90 s”；长隧道群、停车、分段失锁会合并不对，误合并会把真实点替换掉。
   - 怎么做：`TrackStore.gapCandidates` + `GapCandidate` 增加 `merge/split`，重算 A/B、时长、距离、分类；`BatchItem`/`ChangeLog` 复用；候选列表右键菜单、批量窗口行菜单。离线。
   - 工作量与风险：**M**；合并跨真实停车会删真点，必须预览/确认/可撤销，并沿用 `keptInnerPoints` 规则。

3. **补点审阅包导出**（把每处草稿/风险/依据导成 GeoJSON + CSV）
   - 为什么：几十处补点要逐处核对；app 内审阅不够，想用 QGIS / gpx.studio / 表格抽查，或对比两次运行。
   - 怎么做：`RouteDraft.rawCoords`/`crossDrafts` + `FillPlausibility.metrics/reasons` + `BatchItem`；新增 `ReviewPackageExporter` 写 FeatureCollection/CSV；复用 `GPXWriter` 文件写入模式；可选 HTML 表。离线；OSM 几何保留 ODbL 署名；不含 Apple 底图。
   - 工作量与风险：**S**；大文件 JSON 内存、坐标精度、导出含精确位置需注意隐私。

4. **批量补点断点续跑**（任务和已取草稿落盘，退出/崩溃/限流后可续跑）
   - 为什么：铁路批量 16–18 分钟、全量几百处；中途退出只能重跑，公共服务请求浪费且可能触发限流。
   - 怎么做：`BatchState`/`BatchItem`/`RouteCache` 加 Codable DTO，按 track id + 文件指纹写 app 容器 `Caches/BatchResume/`；恢复时按 `(tA,tB,lat,lon)` 校验，失效项标灰；复用 `RouteCacheKey` 稳定哈希。离线。
   - 工作量与风险：**M**；外部改文件导致下标失效、OSM 数据过期；显示“恢复自 X”并允许丢弃。

5. **静止段清理/抽稀**（压缩静止时的重复/漂移点）
   - 为什么：手机室内反复写同一缓存坐标、Garmin 静止漂移会让热力图/迷雾出现假热点，文件也变大；现有回放点/乱跳清理只处理移动中的假点。
   - 怎么做：`TrackData` 速度 + 滑动窗口（<1–2 km/h、半径 <10–20 m、持续 >N 分钟），保留首/末/每 N 分钟一个点；`deleteMode` 预览，`ChangeLog.kind = .deletion` 记“静止压缩”，可还原。离线。
   - 工作量与风险：**S/M**；等红灯/停车/渡轮会被压缩，默认保守、预览、可调，不动速度 >5 km/h 的点。

6. **数据体检报告**（载入后给时间/坐标/重复/超速/断档统计）
   - 为什么：多年备份来自不同 app，常见重复时间戳、乱序、缺时间/海拔、瞬移、重复点；先知道脏在哪，再决定补/删。
   - 怎么做：新增 `TrackHealth` 后台扫描 `TrackData`：NaN、时间有序、重复时间戳/坐标、dt/步长分布、超速、断档、回放/乱跳计数；复用 `GapDetector`/`DiffCompare` 哈希；表格 + CSV。离线。
   - 工作量与风险：**S/M**；百万点多一趟扫描，按 track id 缓存；指标要解释，不自动改。

**分析与统计**

7. **行程/每日摘要**（按天/按行程给出距离、时长、爬升、均速、到访地区）
   - 为什么：用户整理多年足迹，想知道“这天/这趟走了多少、去了哪些国家/省”，现在只有点和断档。
   - 怎么做：`Trip` 已有 range/km/v50/v95；新增 `TrackSummaryBuilder` 用 `GeoCompute.haversine`、海拔平滑/阈值、移动时间定义；`RegionStats` 给国家/省；按时间筛选分组，导出 CSV；控制面板卡片/独立窗口。离线。
   - 工作量与风险：**S/M**；海拔噪声导致爬升虚高，移动/停顿定义要写明，缺时间数据降级。

8. **速度/海拔剖面图**（图表与地图联动）
   - 为什么：补点、乱跳、隧道判断都看时间和速度；现在只能悬停单点。
   - 怎么做：新增 `TrackProfileView`（SwiftUI Canvas），按 ~2k 桶 min/max 抽稀百万点；x = 时间/距离，y = 速度/海拔；叠加断档区间和补点；点击 `selectPoint`/`flyTo`；独立 ObservableObject，避免 ContentView 重算。离线。
   - 工作量与风险：**M**；性能/抽稀、时间缺失、与时间筛选联动。

9. **年度回顾与活动日历**（年度/月度距离、新增国家/省、迷雾增长）
   - 为什么：世界迷雾用户的核心乐趣是“今年探索了什么”；现在只能看当前视图。
   - 怎么做：时间筛选 + `RegionStats` + `FogArchive.genInfo`；日历热图、年度对比表；导出 PNG/CSV。离线。
   - 工作量与风险：**M**；时区、`.fwdb` 代序时间近似、多存档并集按代合并。

10. **补点质量统计面板**（risk 分布、来源、失败原因、缓存命中）
    - 为什么：批量几十处后想知道 high/medium 多少、哪类路/国家容易错；现在只有逐项徽标。
    - 怎么做：聚合 `BatchItem.plausibility`/`status`/`source`/`cross`/`requestsByHost`/`cacheHits`；按 `RegionIndex` 给锚点国家；批量第 3 步/修改记录加统计卡，导出 CSV。离线。
    - 工作量与风险：**S**；口径必须与现有 counts 一致，待选项/失败项分开统计。

11. **迷雾增长时间线**（面积/等级随时间变化）
    - 为什么：`FogArchive.genTimes` 已有但只用于时光机；用户想看“哪年探索了多少”。
    - 怎么做：`FogArchive.genInfo` 按代累计 cells/area/level，画曲线/柱状；GPX 迷雾按时间筛选分桶；`FogStats` 公式复用。离线。

#### 3. 我最推荐的 5 条

1. **双设备互证补点** —— 用户天然有 Garmin + 手机两份数据；这是唯一能拿到“真实隧道几何”的来源，完全离线，直接命中最大痛点，且现有 `tunnelprobe` 已证明思路可行。
2. **修改记录持久化** —— 补点/删除是长期整理，关 app 就丢失证据和还原能力不可接受；它是“敢用自动补点”的信任基础。
3. **行程/每日摘要** —— 把原始点变成“这天走了多少、去了哪”的答案；数据已在 `TrackData`/`Trip`/`RegionStats` 里，风险低、感知强。
4. **断档候选手动合并/拆分** —— 自动隧道群规则有边界，误合并会替换真实点；一个小 UI 能显著减少错补，和现有批量审阅/风险分互补。
5. **补点审阅包导出** —— 几十处补点需要外部核对/留档；实现小，能把“审阅”从 app 内扩展到 QGIS/表格，且不增加联网。

#### 5. 不建议做的

- **云同步/账号体系**：单用户本地工具，数据是精确位置；引入后端/账号只会增加隐私与运维成本，iCloud Drive 手动同步足够。
- **AI/LLM 自动补点或路线生成**：公共路网服务条款/限流先不谈，补点错一处就是删真点；现有“路网 + 风险分 + 人工审阅”更可解释。
- **写回/生成 `.fwdb`**：格式是逆向的，写坏用户的世界迷雾存档不可逆；只读导入是正确边界。
- **Google 地图底图**：需要密钥计费，条款禁止在 Google SDK 之外使用其瓦片；现有 Apple + OSM/OpenTopoMap/Esri 已覆盖。
- **批量下载/离线 OSM 瓦片包**：OSMF 瓦片政策禁止 bulk download；存储巨大，现有按视野 + 300 MB 缓存足够。
- **上传轨迹到 OSM/Strava/社交**：隐私、OAuth、社区规范都是负担；用户要的是本地整理，不是社交。
- **完整 OSM 编辑器/路径编辑**：JOSM/gpx.studio 更合适；本 app 做“选路网草稿 + 微调”即可。
- **用 MapLibre 重写整套地图/地球/快照/视频**：成本远超收益；现有 MapKit + Metal 已解决无缝缩放、地球、导出。
- **自动把所有断档都补上、无审阅落地**：即使两路一致也可能同源错误；风险分/审阅/还原是产品护城河，不能为“一键”牺牲。
- **3D 第一人称飞行/游戏化**：与“整理备份”的定位不符；现有像素地球/时光机已足够表达。
