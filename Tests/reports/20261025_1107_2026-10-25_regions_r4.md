**现象**

- 没有出现 `ready=true + totalCells=0`，也没有崩溃。

**复现步骤**

```sh
  "regionstate" "sleep 50" "regionstate" "sleep 50" \
  "regionstate" "sleep 50" "regionstate"

# 4) 换轨迹：open 后立刻发 5 次 regionstate，间隔 50 ms
python3 Tests/ui/ui.py \
  "open $C/regions/synthetic_regions_track.gpx" \
  "regionstate" "sleep 50" "regionstate" "sleep 50" \
  "regionstate" "sleep 50" "regionstate" "sleep 50" \
  "regionstate"
```

**期望 vs 实际**
- 期望：打开新数据源后的第一次 `regionstate` 已经是 `ready=false` 或新数据报告。
- 实际：第 1、2 次仍是旧报告（1013 或 802304），从第 3 次起才 `ready=false`，之后出现新报告。
- 根因（只读代码定位）：`GPXPointViewer/TrackStore.swift` 的 `loadFwdb`（约 162–212 行）和 `load`（约 910–971 行）在开始解析时没有立即作废旧报告；`invalidateRegionReport()` 只在解析完成后的 `apply(track:)`（约 1057–1061 行）或 `clearTrack()`（约 1122–1126 行）中调用。因此同一批命令在前 50–100 ms 读到的仍是旧 `regionReport`。
- 影响：用户实际可见时间很短（约 0.05–0.1 s），但按本轮任务书“第一次读到的就已不是旧报告”的判定为失败。

### 问题 2：第 3 项最终 `totalPoints=310` 与“手动口径记忆”设计冲突（需任务书确认）

**现象**
- 按任务书第 2、3 项的连续序列执行后，最终 `regionstate` 为：
  ```json
  {"ready":true,"mode":"fog","modes":["points","fog"],"totalCells":1013,"totalPoints":0}
  ```
  而不是期望的 `ready=true, totalPoints=310`。
- 继续执行 `regionsmode points` 后立刻得到 `mode=points, totalPoints=310`，说明点口径报告和新轨迹数据本身是正确的。

**复现步骤**
```sh
# 完整序列见问题 1 的复现步骤 1–4；在第 4 步之后再执行：
python3 Tests/ui/ui.py "regionstate"
# {"ready":true,"mode":"fog","modes":["points","fog"],"totalCells":1013,"totalPoints":0}

python3 Tests/ui/ui.py "regionsmode points" "sleep 1500" "regionstate"
# {"ready":true,"mode":"points","modes":["points","fog"],"totalPoints":310,...}
```

**期望 vs 实际**
- 期望：最终 `ready=true, totalPoints=310`。
- 实际：最终 `ready=true, mode=fog, totalPoints=0, totalCells=1013`。
- 原因：第 2 项准备阶段的 `regionsmode fog` 会被 `TrackStore.pickRegionsMode` 记为“手动口径”；存档打开时强制 `fog`；离开存档后 `autoRegionsMode()` 按设计恢复手动选择 `fog`（`TrackStore.swift` 约 439–441、511–525 行有明确注释）。因此只要不先切回点口径，迷雾报告的 `totalPoints` 就是 0。该行为与第 3 轮第 6 项“手动口径的值被记住”一致。
- 判断：这更像**任务书期望与既有设计冲突**，不是可直接判定的代码缺陷。若产品希望离开存档后强制回到点口径，才需要改代码；否则建议任务书在第 3 项末尾加一条 `regionsmode points`，或把期望改为 `totalCells=1013`。
- 本条未通过“改期望”来变绿，也没有改代码。
