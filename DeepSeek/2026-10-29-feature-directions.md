# 每日/行程摘要与后续功能方向

2026-10-29。这是下一阶段建议，本轮没有实现新功能。架构判断由 GPT-6 Astra / ultra 完成，主代理整理；[详细设计边界](../Tools/agents/records/2026-10-29-deepseek-response/coordinator/architecture-decision.md)。

## 优先做：每日 / 行程摘要

这个方向值得做。现有时间筛选、轨迹分段、地区统计、修改记录能提供输入，但摘要应有独立的统计规则，不能直接把补点模块的 Trip.km 当作全天总里程。

首版建议：日历列表和行程列表，每项显示开始/结束、距离、记录跨度与移动时间、爬升/下降、到访国家地区、交通方式。点击摘要即可定位地图并切换时间范围；允许合并/拆分行程、修正交通方式，导出 CSV。先把数字做得可解释，再考虑自动生成游记。

| 字段 | 必须说清的口径 |
|---|---|
| 日期 | 明确本机/固定时区/UTC；跨午夜切分，兼容夏令时23/25小时日。不能把本机时间冒充轨迹所在地时间。 |
| 里程 | 同源段内有效边累计；不跨断档或不同轨迹段连线。原始记录的折线距离与补点估算距离分列；缺记录不算零距离。 |
| 时长 | 分开记录跨度、连续观测时间、移动、停留、未知断档；没有记录不自动视为停留。 |
| 爬升/下降 | 明确平滑/噪声阈值和海拔覆盖率；海拔不足时显示不可可靠计算，避免把GPS高度抖动累加成巨大爬升。 |
| 国家地区 | 复用离线地区索引，保留边界/海岸精度限制；无归属点可见，不强行吸附到邻国。 |
| 交通方式 | 按段展示步行/骑行/公路/铁路等候选，附置信度并允许人工修正；速度相近不能单独证明交通方式。无法判断时显示未知。 |
| 多设备 | 默认按来源分别统计；合并需要选择主记录或去重规则，不能把两台设备重叠记录的里程相加。 |
| 证据来源 | 标明原始记录、合成补点、缺失字段和所用规则版本。`.fwdb`只有格子与区块文件修改时间，不生成伪造的每日里程或首次到访日期。 |

实现时建立纯数据的 SummaryBuilder，以数据修订、来源、时区和规则版本做缓存键；后台计算沿用发布归属校验。界面只展示不可变结果，这也能自然形成一个清晰模块，而不用先大拆现有巨型文件。

## 另外值得加的五项

1. **保存与恢复项目会话。** 保存导入文件引用、筛选、显隐、补点草稿和修改记录，重启后继续编辑。这比仅导出GPX更能保护已经投入的整理工作。若当前经常批量修补轨迹，它与摘要同优先级。
2. **分享前隐私裁剪。** 预览隐藏起终点附近或自定义区域，也可移除绝对时间；只生成分享副本，删点后不跨隐藏区域连线。可统一用于GPX、图片和视频导出。
3. **导入质量报告。** 一页汇总缺时间/海拔、重复来源、时间倒退、稀疏采样、断档及补点占比，点击定位问题。让用户先知道哪些统计可信，再决定是否修复。
4. **两期探索增量。** 比较两份迷雾存档或两组轨迹的新增/重叠/减少格子，按地区显示新增面积。日期不可靠时只写“快照A→B”，不虚构每天的探索历史；这与已有逐点轨迹差异对比不同。
5. **地点与停留书签。** 给行程节点或地点添加名称、备注，按地点检索历史到访并跳转摘要。自动停留仅作为可修正候选，不自动猜测“家”“公司”等地点含义。

建议顺序：摘要与项目会话优先，其次隐私裁剪和质量报告，再做探索增量、地点书签。多设备自动融合放到后面：时间偏差、来源冲突和重复观测都需要独立设计，不能当作简单的合并开关。
