## N04：为什么不能直接给 GeoCoord 加全局偏移

当前源码并没有一个已经统一完成的地图坐标边界：

- `GapFill.swift:17–23` 的 GeoCoord 只是恒等挂点。其调用点仅见主地图草稿拖动/草稿投影以及审阅草稿，不涵盖所有显示、拾取、套索、地图折线、地区边界和图片/视频。
- `GeoCompute.swift:71` 用原始经纬度直接算 Web Mercator；主平面渲染在 `PointMapView.swift` 的 performRedraw 使用 visibleMapRect/world 构造 CameraRect，hitTest（约3179）也把鼠标按同一矩形映射到原始 Mercator。仅改变 GeoCoord 会让草稿和点云走不同管线。
- `MapSources.swift:37–94` 直接按 XYZ 获取 OSM/OpenTopoMap/Esri；外部图作为 MKTileOverlay 覆盖 Apple。快照/视频/3D 地面又会按 appleFallback 回退 Apple（docs/map-sources.md），不能只看主窗口当前下拉选项。
- Apple 官方定义 CLLocationCoordinate2D 使用 WGS 84；这只是公共 API 坐标契约，**不能证明本机当前大陆底图的内部纠偏/投影行为**，也不能证明自绘 Metal 已经正确对齐。[Apple 坐标定义](https://developer.apple.com/documentation/CoreLocation/CLLocationCoordinate2D)
- OSM 原始坐标和瓦片投影分别为 WGS-84、Web Mercator；Esri World Imagery 的官方说明也是 Web Mercator Auxiliary Sphere。因此全局 GCJ 变换没有依据。[OSM 投影](https://wiki.openstreetmap.org/wiki/Projection)、[Esri World Imagery](https://doc.arcgis.com/en/data-appliance/2023/maps/world-imagery.htm)
- 高德官方服务使用 GCJ-02，但“高德服务的坐标系”不能替代“MapKit 在这个 macOS 环境的 API 与自绘层到底如何变换”的证据。[高德 FAQ](https://developer.amap.com/faq/advisory/others/39838)

**选择**：本轮不启用新转换。若后续有大陆使用需求/实际错位样本，最小下一步是记录 macOS/MapKit 环境、实际提供者和已知 WGS-84 输入，比较同一点的原生 annotation、Metal 点、草稿与鼠标往返，在 Apple 标准/影像/混合及一个 WGS 瓦片来源各检查；另比较相同区域快照。需先区分数据原本就是 GCJ、平台内部转换、或者自绘投影绕过平台三种成因。确认后才把“数据 ↔ 地理坐标 ↔ 平面显示 ↔ 屏幕”边界按来源集中，并覆盖反变换、缓存失效、各渲染路径与非大陆不变。不要用大矩形判断“中国”后统一偏移，不动统计、原始列、路网请求或导出坐标。

本次没有执行上述平台/像素验证，不把缺少实证说成“已证明完全没有偏移”。

## N05：fwdb 日期只能表示存档区块修改时间

`FogArchive.swift:103–143` 从每个区块的 `contentModificationDate` 读取 mtime，排序成 genTimes；整区块所有格共享一个 generation。合并存档对重复格取更早代（同文件约147–177）。`TrackStore.swift:410–447` 用这份代序打开时光机，`PlaybackBarView`（ContentView 约2485）显示普通日期，`VideoExport.swift:371,415` 给成片画普通日期。

这能做“按存档元数据组织的近似回放”，不能表示逐格首次探索日期。文件系统修改时间甚至不一定等于实际同步发生时刻，复制/恢复/同步工具可能改变它。源码/README 的“唯一真实时间线”表述过强。

建议最小文案：

- 回放条日期旁显示简短且可见的“近似时间”，悬停解释“按存档区块文件修改时间排列；同一区块同时出现，不能表示实际探索日期”。
- 入口提示依数据源区分：GPX 按记录时间；fwdb 按区块修改时间近似回放。
- 视频导出面板保留完整说明，成片日期加“近似”或同等标记，避免视频离开 app 后丢掉限制说明。
- README/FogArchive 注释同步更正即可；无需改数据、重排 generation 或伪造时间戳。

日/年摘要不要对 fwdb 输出“某天走了多少公里/第一次到达哪里”。多个带确定保存日期的独立快照可以比较“两个存档快照之间新增格子”，也只能归到这个区间，不能把新格分摊成每日。

## N22/N24/N29：先说明证据边界

**N22**：GPXWriter 多段分支（49–64）串行构造段缓冲，单段分支（68–96）才并行。Data(bytes) 的复制还出现在单段路径，不能说只有多段才多一次。串行不影响段边界正确性，实际总耗时尚未量化。以后若明显慢，应在保持原段序/原子写出的前提下复用有界格式化任务；仅“每段并行”会对很多小段制造过多任务，且单个巨大段仍缺并行度。

**N24**：固定容量是 `32768+515*16384=8,470,528` B/并发任务。Data(count:) 语义要求零初始化，但不能单凭源码断言系统一定实际写满每页或清零就是主耗时。并发解析所有区块也不意味着全部区块的8.47MB同时驻留。按 comp.count*8 不能保证解压上界，极高压缩比必须有格式上限、容量耗尽与损坏输入的区分，重复解压还有成本。现有上界是格式明确有界，未有慢样本/内存证据，先保留。

**N29**：TrackStore.load 的 slice（约1041）以及 rebuildDisplayTrack 的 mergeParsed 确有复制；但原解析对象、留底与显示对象生命周期不同，不能直接把“两次复制”相加为实测峰值。retain per-file parsed 用于模式切换、编辑与重建；mergeParsed 还赋 fileID、重映射segmentID、生成sortedRuns并累加来源元数据。未来单文件快路可利用 Swift Array 的 CoW，共享未修改列，但必须保持这些契约，且验证追加第二文件、编辑后重建、失败文件、多段/缺时间点的行为。不能直接绕过整个 ingest/rebuild 只设置名字。

三项目前都没有必要为“独立确认”跑新性能测试。若用户实际报告大档操作慢，再以具体样本、构建哈希、阶段耗时/峰值为触发，做各自最小测量。

## 每日/行程摘要：建议优先做，但先固定统计口径

这是有价值且范围可控的新功能；现有时间筛选、TripSegmenter、RegionStats、Gap/ChangeLog 提供大部分输入，但不能直接把现有 Trip.km 当“全天总里程”。

- **最小首版**：日历列表/行程列表 + 每条开始/结束、记录跨度、可确认轨迹距离、断档时长、原始/合成点数、到访地区；点击联动地图和时间筛选，支持表格导出。先展示可复核数字，不需要模型生成游记。
- **日期与时区**：显式选择“本机时区（默认）/固定时区/UTC”，写入摘要缓存键与导出。按日历自然日分桶，处理DST的23/25小时日，不能固定除86400假设每天等长；跨午夜的同段有效边按时间界点切分。当前 RegionStats 用 TimeZone.current，与“轨迹所在地当地时间”不是同一概念，不能悄悄冒充后者。
- **距离**：仅同一源段内的可信相邻边累计；跨段、未知时间、异常跳点和断档分别展示。稀疏轨迹连接得到的是折线估计，不能称真实路程。已补点路径单列“估算补全距离”，避免和原始观测混成同等真实。
- **时间**：区分首末记录跨度、已观测的连续时间、移动时间、停止与未知断档。移动/停留需显式阈值和噪声策略；不要把没记录的10分钟自动计为停留。
- **现有 Trip 边界**：GapFill.swift:1018 当前为150m内10分钟停留/10分钟记录空白切分；服务补点路型推断。Trip.km 只计 `0<dt<=60s && v<=350km/h` 的步；v50/v95基于移动步，既不是全天距离也不是时间加权均速。可复用源段与候选边界，摘要应拥有独立、版本化统计规则，允许用户合并/拆分行程，不改原数据。
- **多设备重叠**：优先按来源分别摘要；选择“合并旅程”必须指定主记录或明确去重规则，否则双份记录会重复计算里程、时间和行程数。不能把时间重叠就认成同一人同一条路。
- **缺数据**：无时间点单列“日期未知”，不塞到某一天；无/部分海拔时不展示可靠爬升。fwdb 仅提供总格/面积与快照间差值，不能给逐日行程或里程。
- **实现边界**：做纯数据的 SummaryBuilder/策略对象，按数据修订+选择源+时区+规则版本缓存；后台运算沿用 publication token。UI只观察完成的不可变报告，不把统计算法继续塞进ContentView；这会自然为后续模块化提供一个小边界。
